LỜI MỞ ĐẦU

Trong bối cảnh các dịch vụ giải trí ngày càng được cung cấp trực tuyến, việc tra cứu phim, chọn suất chiếu và đặt chỗ qua mạng giúp khán giả chủ động hơn, đồng thời giúp đơn vị vận hành quản lý lịch chiếu và tình trạng ghế hiệu quả. Đề tài xây dựng một hệ thống đặt vé xem phim gồm các dịch vụ API phía máy chủ và ứng dụng web client tiêu thụ các API này.

1. Lý do chọn đề tài

Quy trình đặt vé thủ công hoặc qua nhiều kênh rời rạc thường khiến khách khó theo dõi lịch chiếu, tình trạng ghế và thông tin đặt chỗ. Khi nhiều người cùng chọn một ghế, hệ thống cần có cơ chế giữ chỗ và xác nhận nhất quán. Đây là bài toán phù hợp để vận dụng thiết kế REST API, phân tách dịch vụ nghiệp vụ và tích hợp client-server.

2. Mục tiêu nghiên cứu

Mục tiêu tổng quát là phân tích, thiết kế và hiện thực một hệ thống đặt vé có thể chạy cục bộ, trong đó React giao tiếp qua API Gateway với các dịch vụ Spring Boot. Các mục tiêu cụ thể gồm quản lý tài khoản và phân quyền cơ bản; tra cứu phim, rạp, phòng, suất chiếu và sơ đồ ghế; giữ ghế có thời hạn; tạo, xác nhận, tra cứu và hủy booking; cung cấp giao diện quản trị danh mục.

3. Phạm vi nghiên cứu

Phiên bản hiện tại tập trung vào quy trình đặt vé và quản lý dữ liệu danh mục cơ bản. Hệ thống có đăng ký/đăng nhập, JWT, danh sách phim, chi tiết phim, chọn suất/ghế, xem booking; chức năng quản trị phim, ảnh poster, rạp, phòng và suất chiếu. Thanh toán trực tuyến, gửi email/SMS, ứng dụng di động, triển khai cloud và tích hợp hệ thống rạp bên ngoài không thể hiện trong mã nguồn được khảo sát nên được xem là ngoài phạm vi phiên bản này.

4. Phương pháp nghiên cứu

Nhóm khảo sát bài toán, xác định tác nhân và quy tắc nghiệp vụ, thiết kế kiến trúc phân tán theo dịch vụ, thiết kế dữ liệu/API, hiện thực backend và client, sau đó xây dựng các kịch bản kiểm thử chức năng và tích hợp. Báo cáo mô tả trạng thái theo mã nguồn hiện có; những kết quả chạy thử cần được bổ sung bằng ảnh/chứng cứ thực nghiệm của nhóm.

5. Cấu trúc báo cáo

Báo cáo gồm bốn chương: cơ sở lý thuyết và công nghệ; phân tích và thiết kế; cài đặt và triển khai; kiểm thử và đánh giá. Cuối báo cáo là kết luận, tài liệu tham khảo và phụ lục đề xuất.

CHƯƠNG 1. CƠ SỞ LÝ THUYẾT, CÔNG NGHỆ VÀ GIẢI PHÁP

1.1. Kiến trúc Client–Server và hướng dịch vụ

Ứng dụng client chịu trách nhiệm hiển thị giao diện và gửi yêu cầu; backend cung cấp dữ liệu, xác thực và xử lý nghiệp vụ. Hai phía trao đổi qua HTTP với dữ liệu JSON. Dự án chia backend thành các dịch vụ theo miền nghiệp vụ: xác thực, phim, lịch chiếu/ghế và booking; API Gateway làm đầu mối định tuyến và kiểm tra JWT.

Cách phân rã này mang đặc điểm của kiến trúc dịch vụ/Microservices ở mức bài tập: mỗi dịch vụ có trách nhiệm nghiệp vụ và cấu hình cơ sở dữ liệu riêng. Các dịch vụ hiện chạy cục bộ, không có cơ chế điều phối triển khai hay khám phá dịch vụ chuyên dụng; vì vậy báo cáo xem đây là hệ thống hướng dịch vụ phân tách theo miền, chưa khẳng định các đặc tính vận hành production của Microservices.

1.2. RESTful Web API

API biểu diễn tài nguyên bằng đường dẫn danh từ như /api/movies, /api/showtimes và /api/bookings. GET dùng để đọc, POST để tạo hoặc thực hiện hành động nghiệp vụ, PUT để cập nhật, DELETE để xóa. Dữ liệu trao đổi chủ yếu là JSON; ảnh poster được tải lên dạng multipart/form-data. Các mã HTTP được dùng theo ngữ cảnh như 200, 201, 204, 400, 401, 403, 404, 409 và 410.

Client gọi API qua Axios. Token JWT được thêm vào Authorization: Bearer ở interceptor; phản hồi lỗi được chuyển thành thông báo giao diện. Gateway xác thực token, loại bỏ các header định danh do client tự gửi, sau đó tự gắn X-User-Id và X-Role tin cậy cho dịch vụ phía sau.

2.5. Thiết kế API dịch vụ

2.5.1. Quy ước API

Base URL phía client mặc định là http://localhost:8080. Dữ liệu JSON dùng UTF-8; request có nội dung gửi Content-Type: application/json, ngoại trừ tải poster dạng multipart. API cần token dùng Authorization: Bearer <JWT>. Gateway chuyển tiếp user identity qua X-User-Id và role qua X-Role. Các endpoint /internal không được public qua Gateway.

2.5.3. Đặc tả API tạo booking

POST /api/bookings yêu cầu Authorization Bearer. Body ví dụ: {"showtimeId": 12, "seatIds": [101, 102]}. Gateway cung cấp X-User-Id sau khi xác thực. Khi thành công, API trả HTTP 201 và BookingResponse gồm bookingId, thông tin phim/rạp/phòng, giờ chiếu, danh sách ghế, tổng tiền, trạng thái PENDING và thời điểm hết hạn giữ. Ghế tranh chấp trả 409; token thiếu/sai trả 401; dữ liệu không hợp lệ thường trả 400; lỗi dịch vụ phụ thuộc có thể trả 5xx.

3.2. Cài đặt Backend Service/API

3.2.1. Cấu trúc dự án Backend

Project Maven cha cinema-booking quản lý các module auth-service, api-gateway, movie-service, showtime_db (artifactId là showtime-service) và booking-service. Các module nghiệp vụ dùng cấu trúc controller/service/repository/entity/dto; gateway có filter JWT và cấu hình route. Cấu hình mặc định cài đặt cổng lần lượt 8081–8084, Gateway 8080.

3.2.2. Mô hình dữ liệu và truy cập CSDL

Entity được ánh xạ bằng JPA; Repository kế thừa JpaRepository và dùng derived query hoặc JPQL/native query. Cấu hình datasource nằm trong application.yml của từng module. db/init.sql tạo bốn database và user MySQL theo từng service. Trong cấu hình hiện tại, application.yml từng dịch vụ đang kết nối localhost bằng tài khoản root; khi chạy cần bảo đảm khớp với môi trường MySQL.

3.2.3. Hiện thực API và nghiệp vụ chính

Luồng đọc dữ liệu đi từ Controller → Service → Repository → MySQL → DTO/JSON. Ví dụ MovieController nhận GET /api/movies và gọi MovieService; ShowtimeController trả suất chiếu và sơ đồ ghế; BookingController nhận userId do Gateway gắn và gọi BookingService.

Giữ ghế được hiện thực bằng câu lệnh cập nhật có điều kiện trong ShowtimeSeatRepository: chỉ chuyển sang HOLDING nếu ghế AVAILABLE hoặc HOLDING đã hết hạn. Số ghế được cập nhật phải bằng số ghế yêu cầu; nếu không, transaction rollback để tránh giữ một phần. Confirm chỉ đổi ghế khi booking còn giữ hợp lệ. Thao tác lặp lại confirm cho booking đã xác nhận được xử lý idempotent ở tầng dịch vụ.

BookingService tạo booking PENDING trước khi gọi Showtime. Sau khi giữ ghế, dịch vụ lưu snapshot thông tin và giá ghế. Nếu lỗi giữa chừng, gọi release để bù trừ. Hết hạn chuyển trạng thái EXPIRED và nhả ghế; hủy booking yêu cầu chủ sở hữu và áp dụng điều kiện thời gian hủy với booking đã xác nhận.

3.2.4. Xác thực và phân quyền

AuthService lưu mật khẩu đã băm BCrypt và phát JWT chứa userId, role, subject và thời hạn. Gateway xóa các header X-User-Id, X-Role, X-Internal-Token client tự gửi trước khi xử lý, chặn đường dẫn /internal, xác thực chữ ký JWT và bổ sung header tin cậy. GET danh mục và đăng nhập/đăng ký là công khai; thao tác ghi phim/rạp/phòng/suất yêu cầu ADMIN. Endpoint booking đòi token.

3.3. Cài đặt Client Application

3.3.1. Cấu trúc dự án

Thư mục frontend/src gồm App.jsx và main.jsx làm khung ứng dụng; api.js tập trung Axios client, interceptor và hàm định dạng; pages chứa Movies, MovieDetail, SeatPicker, Login, MyBookings và Admin. index.css định nghĩa giao diện. Vite cung cấp máy chủ phát triển.

3.3.2. Giao diện và chức năng

Movies hiển thị phim đang chiếu/sắp chiếu; MovieDetail trình bày phim và lựa chọn lịch; SeatPicker hiển thị ghế, chọn ghế, tổng tiền, đếm thời gian giữ và cho phép xác nhận/hủy; MyBookings hiển thị booking; Admin cung cấp biểu mẫu quản trị danh mục. Thành phần bảo vệ route kiểm tra token/role phía client để cải thiện trải nghiệm, song Gateway mới là lớp bảo vệ API.

3.3.3. Tích hợp Client với API

Axios dùng base URL VITE_API_URL, mặc định http://localhost:8080. Interceptor request tự thêm Bearer token lấy từ localStorage. Interceptor response chuyển lỗi 401 ở API nghiệp vụ về màn hình đăng nhập; hàm errMsg lấy thông báo nghiệp vụ từ response. SeatPicker tải lại trạng thái ghế định kỳ mỗi 8 giây, hiển thị đồng hồ theo holdExpiresAt và gửi thao tác tạo/xác nhận/hủy booking tới backend.

3.3.4. Trạng thái và lỗi

Các màn hình lưu dữ liệu vào state React, hiển thị thông báo lỗi qua errMsg và làm mới danh sách sau thao tác. Mã nguồn thể hiện xử lý chuyển hướng khi phiên hết hiệu lực và tải lại trạng thái ghế. Trạng thái loading, skeleton và thông báo rỗng có thể được rà soát bổ sung theo từng màn hình khi hoàn thiện nghiệm thu.

3.4. Triển khai hệ thống

README hướng dẫn chạy MySQL bằng db/init.sql, mở project bằng JDK 21 và nạp Maven, sau đó khởi chạy Auth, Movie, Showtime, Booking và Gateway; cuối cùng chạy npm install và npm run dev trong frontend. Client mặc định ở cổng 5173. Thứ tự này giúp các dịch vụ phụ thuộc đã sẵn sàng khi nhận request. Thông tin database, JWT secret và internal token trong cấu hình hiện là giá trị phục vụ phát triển cục bộ; môi trường thực tế cần cấu hình bằng biến môi trường.

CHƯƠNG 4. KIỂM THỬ VÀ ĐÁNH GIÁ HỆ THỐNG

Repository có cấu hình Postman globals nhưng không có bộ test tự động hoặc biên bản kết quả kiểm thử được lưu kèm. Do đó bảng dưới đây là kế hoạch/tiêu chí kiểm thử để nhóm thực hiện và ghi nhận kết quả, không khẳng định các ca đã chạy thành công. Bổ sung ảnh Postman, ảnh giao diện và log chạy thật trước khi nộp báo cáo.

KẾT LUẬN VÀ HƯỚNG PHÁT TRIỂN

Đề tài đã xây dựng nền tảng đặt vé xem phim theo hướng dịch vụ, gồm API Gateway và bốn dịch vụ nghiệp vụ; frontend React gọi API tập trung; dữ liệu được chia theo từng dịch vụ. Các chức năng cốt lõi được thể hiện trong mã nguồn gồm xác thực JWT, quản lý phim/rạp/phòng/suất, sơ đồ ghế, giữ ghế có thời hạn, tạo/xác nhận/hủy booking. Quy tắc giữ ghế nguyên tử và cơ chế bù trừ khi quy trình liên dịch vụ thất bại là phần xử lý nghiệp vụ đáng chú ý.

Hạn chế hiện tại gồm chưa có thanh toán trực tuyến, thông báo khách hàng, triển khai cloud/containers, tự động hóa kiểm thử và quan sát tập trung. Một số cấu hình phát triển còn khai báo trực tiếp trong YAML; cần chuyển sang biến môi trường và quản lý bí mật an toàn khi triển khai. Báo cáo cũng cần được bổ sung thông tin nhóm, môi trường thực tế, ảnh giao diện và kết quả các ca kiểm thử trước khi nộp.

Hướng phát triển phù hợp gồm tích hợp cổng thanh toán với trạng thái giao dịch và idempotency; bổ sung kiểm thử tự động cho API và tình huống tranh chấp; đóng gói Docker Compose để khởi chạy đồng bộ; quản lý secret theo môi trường; bổ sung logging/monitoring; mở rộng thông báo email và client di động khi có nhu cầu.
